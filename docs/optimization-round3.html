P1 值得做 启动自动拉取：无变化检测，每次都全量下载 + 合并

现状

应用启动约 6 秒后会执行一次自动拉取。代码路径是 auto_sync_on_startup → run_oss_download：

// src-tauri/src/commands/sync.rs:328
let (wh_key, rd_key) = oss.snapshot_keys();
let wh_exists = oss::head_object(&client, &oss, &wh_key).await?;   // 2 次 HEAD，廉价
let rd_exists = oss::head_object(&client, &oss, &rd_key).await?;
...
let wh_bytes = if wh_exists {
    Some(oss::get_object(&client, &oss, &wh_key).await?)        // ← 无条件全量 GET
} else { None };
let rd_bytes = if rd_exists { Some(oss::get_object(...).await?) } else { None };
// 然后：落盘临时快照 → 记录级合并进本地库 → invalidate_stats

问题在于：head_object 只返回 Result<bool>（对象在不在）， 把 OSS 在 HEAD 响应里本来就给的 ETag 丢掉了。 于是代码知道"远端有快照"，却完全不关心"远端快照是不是还是我上次导入的那一份"。

这 622 ms 里在做什么

区间宽度为示意，非精确分段计时；唯一精确的实测值是总耗时 622 ms。

为什么要紧

  • 每次启动固定多花约 0.6 秒在网络上，且完全取决于 OSS 与代理的当前速度——慢网下会明显拉长。
  • 更值得注意的是：它会在启动 6 秒后对数据库做一次写入（合并 + invalidate_stats）。这个时刻用户通常刚开始翻图库，等于给浏览主路径引了一次写锁竞争。
  • 顺带产生一次多余的 OSS 下行流量与计费（量小，但纯属无效）。

修法

  1. 让 head_object 返回 (bool, Option<String>)——顺带把响应头里的 ETag 取出来（OSS 的 HEAD 一定带）。
  2. 在本地记下"上次成功导入的 ETag"（放进 config 或一个小的 state 文件，两个 key 各记一份）。
  3. HEAD 拿到 ETag 后先比对：一致就直接返回"无变化"，跳过 GET、跳过落盘、跳过合并。
为什么 ETag 是可靠信号：OSS 的 ETag 对普通上传就是对象的 MD5，写入内容变了它必然变。 唯一要小心的是分片上传（ETag 形如 <md5>-<n>）——但本项目用 put_object 单次上传，不涉及。

预期收益（估算）：622 ms → 约 150–250 ms（只剩 2 次 HEAD），并消除启动阶段的一次 DB 写入。 准确值需实现后实测。

P2 值得做，但改的是数据链路，需谨慎 退出自动上传：无条件执行，且会卡住关闭

现状

实测

10-02 那次会话：进程 07:03:59 起来，07:04:05.667 就触发了退出上传——用户只开了约 3.5 秒， 数据库不可能有任何变化，但照样把两个快照推了上去：

日志里 5 次退出、5 次上传，无误判记录，也就是没有一次是因为"确实有新数据"才传的。

为什么要紧

  • 常规情况下是浪费 ~250 ms 与一次上行流量（约 350 KB）。
  • 真正的风险在于它同时是退出阻塞点。网络卡住时用户会看到"点了关闭没反应"，最长 15 秒才关掉。 这类问题在慢网/代理异常时才会暴露，日常不易复现。

修法（比"脏标记"更安全的一种）

我上一轮拒绝改这里，理由是"加脏标记、判断错会导致数据不同步"。这个顾虑是对的——脏标记需要在每个写库点挂钩子， 漏一个就静默丢数据。换个更保守的信号：文件级的 mtime + size 比对。

  1. 每次成功上传后，记录两个本地 DB 的 mtime 与 size。
  2. 退出时比对；两者都没变且 WAL 已 checkpoint，就判定"本地无新数据"，直接跳过上传。
为什么这个判据是安全的：任何对 DB 的写入都必然改变 mtime（通常还会改 size）， 所以误判方向只会是"以为变了、实际没变"——最坏结果是多传一次，永远不会漏传。 这正是它可以做、而脏标记不行的原因。
实现时要盯的两点：① WAL 模式下主库文件的 mtime 可能滞后于实际写入 → 必须放在 maintain_on_exit（WAL checkpoint）之后再取 mtime； ② 记录值要与"上次上传成功"绑定，上传失败时不能更新，否则下次会被误判为无变化。

实施结果

两项都已实施并通过验证。实施过程中又查出两个原分析没看出来的真 bug，其中一个正是让 P2 完全失效的原因。

🔴 新发现 1：无变化的合并也会写库

import_*_snapshot 无条件 tx.commit()。逐步骤比对文件哈希定位到：

操作是否改写数据库文件
只开闭 / ATTACH + DETACH / 空事务 COMMIT否
跑两条合并语句 + COMMIT（0 行变化）是
跑两条合并语句 + ROLLBACK（0 行变化）否

不修的话，每次"无变化"的拉取都会把本地库 mtime 改掉 → 退出时必然触发上传 → 新 ETag → 另一台再拉再传， "你传我拉"永不终止。P2 的判据会被这个写入完全抵消。已加 commit_or_rollback()。

🔴 新发现 2：maintain_on_exit 自己没做到它注释里承诺的事

原实现是 wal_checkpoint(TRUNCATE); PRAGMA optimize;——而 optimize 一旦真的要更新统计信息， 它自己也会写库，写入同样滞留在 WAL 里。于是函数返回时 .db 依然不是完整状态、WAL 也没归零， 它注释里写的"直接复制 .db 做备份不会漏掉尚未 checkpoint 的事务"其实没达成。 诊断实测：连读两次该函数，第二次读到的内容与第一次不同（ec8a… → 72f6…）。 补一次收尾 checkpoint（ckpt; optimize; ckpt）后，单次调用即稳定。

🔧 顺带修掉：渲染自检脚本会永久挂起

tests/render-check.mjs 的顺序是「先起静态服务器，再启浏览器」。浏览器启动失败时会在 服务器已监听的状态下抛出，而 main().catch() 只设了 process.exitCode、 没关服务器 → 事件循环永不结束 → 脚本一直挂着不退出（实测白挂 20 多分钟，CI 里等于挂死）。 已把服务器句柄提到模块级、尾部改为关闭后明确 process.exit(code)： 同一场景现在 1 秒退出、退出码 1、诊断清晰。

两点还没实测、需诚实说明： ① 启动耗时的真实降幅（622 ms → 预计 150–250 ms）需要重新构建应用后跑一次才有数字， 单测覆盖不到网络那一段； ② 两台机器之间的实际收敛行为也没法在单机上验证。判据的保守方向（不确认就重下/重传）都写成测试了， 但端到端仍需真机确认。

建议顺序

  • 第一步：P1（ETag 变化检测）。收益明确、完全在同步的"读"方向、失败只影响一次同步，风险最低。
  • 第二步：P2（mtime+size 跳过上传）。顺带解决退出阻塞。实现时严格按上面两个注意点来， 并补一个"改了 DB 就必须上传"的测试作为回归防线。
  • P1 顺带可以复用同一份"上次同步状态"记录，两件事放一起改更省事。
