日期 2026-10-02 代码规模 Rust 10,730 行 / 前端 7,027 行 数据来源 本机 WallHub 数据库 + 缩略图缓存

结论

项目整体工程质量很高——首屏体积、SQLite 分页、JPEG 降采样解码等常见瓶颈都已优化到位，继续在这些方向投入收益甚微。
但存在一个被忽视的架构级问题：缩略图使用无损 WebP 编码，导致缩略图缓存膨胀到 130.8 MB（其中 92% 是可回收或可压缩的）， 同时拖慢了首次浏览时的缩略图生成速度。这是本次分析中收益最大、且易于修复的一项。

实施状态：已完成 —— P0 / P1 / P2 已落地并通过全部验证（后端 129 测试 + clippy 0 警告，前端 39 测试 + 6 视图渲染自检）， P3 经核实后判定不采纳。详见第五节。

P0缩略图使用无损 WebP 编码

这是本次分析中收益最大的发现。缩略图缓存 130.8 MB，而实际源图只有 175 张（约 1 GB），缩略图占源图的 13%——对"缩略图"而言这个比例高得异常。

根因

项目的缩略图以 .webp 扩展名保存，最终走 DynamicImage::save()。而 image 0.25 的 WebP 编码器只实现了无损编码（VP8L），其依赖 image-webp 0.2.4 同样只有 lossless.rs，没有有损编码器：

// image-0.25.10/src/lib.rs:219
/// | `webp`  | WebP     | Only lossless encoding is currently supported.

// image-0.25.10/src/codecs/webp/encoder.rs:12
/// Right now only **lossless** encoding is supported.
/// However, it does not reach the full potential of lossless WebP for reducing file size.

实测验证了这一点——抽样检查 470 个缩略图，469 个的文件头是 VP8L（无损），仅 1 个例外。

修复方案

方案做法优点代价
A（推荐） 引入 webp crate（libwebp 的 C 绑定），用有损编码器 体积/质量最优、编码最快、与现有 .webp 缓存路径一致 新增一个 C 依赖（libwebp-sys 自带源码，本机已有 VS Build Tools 可编译）
B（零依赖） 改存 JPEG（image::codecs::jpeg::JpegEncoder::new_with_quality，q85） 不新增任何依赖，改动最小，可立即实施 体积比有损 WebP 大约 20–30%（仍比现状小 80%）；JPEG 不支持透明通道

方案 B 的透明通道问题风险很低——本机 175 张源图经检查全部为 RGB（无 alpha），且缩略图仅用于网格展示。

实施注意：必须让旧缓存失效。 ensure_thumbnail_inner() 在 dst.exists() 时直接返回旧文件， 改编码后旧的无损缓存不会自动重建。建议在文件名中加编码版本标记（如 __w720q85.webp）， 旧文件即自然失效并被清理逻辑回收，避免手工清理与"改了没效果"的困惑。

P1孤儿缩略图未自动回收

缩略图清理命令 clean_thumbnails 存在且实现正确，但只能由用户在「数据库」页手动点击触发，没有随源图删除自动执行，长任务下载-删除循环后会持续堆积。

reddit 保存目录当前为空（337 条数据库记录中 192 条为 love=1 的"缺失文件"），其 208 个缩略图 / 30.7 MB 全部是孤儿——即使重新下载，这些图也需要重新生成缩略图，缓存没有任何复用价值。

成因（已核实）：应用内的删除路径（dislike_file / delete_orphan_file/files）四处都已经调用了 remove_thumbnails()，所以这些孤儿并非"漏接清理"，而是外部删除造成的——用户在资源管理器里删图、 或用同步工具清空目录时，应用无从感知。
效果：清理可释放 30.7 MB（占缓存 23%）。
已实施：改为启动后延迟自动跑一次保守清理，不再依赖用户手动点击（见第五节）。

P2DPR 档位缓存存在闲置副本

三档缩略图（w240 / w480 / w720）可共存、互不覆盖。当前配置 thumbnail_dpr = 3 是最低档位（floor）语义：

// src/utils/thumbSize.ts:56
const needed = Math.ceil((drawnWidth * COVER_WIDTH_FACTOR * deviceDpr) / THUMB_BASE_WIDTH);
return clampDpr(Math.max(floor, needed));   // floor = 3 → 恒返回 3

由于 Math.max(3, needed) 恒 ≥ 3 且被 clamp 到 3，实际只会请求 w720。w240 与 w480 是用户此前将 thumbnail_dpr 设为 1 或 2 时期生成的遗留缓存，在当前配置下不会再被读取：

档位文件数体积当前配置下
w2401487.4 MB闲置（floor=3 不会请求）
w48014626.4 MB闲置（floor=3 不会请求）
w72017568.7 MB在用
合计469102.5 MB33.8 MB 可回收

效果：释放 33.8 MB。
注意：这是配置相关的结论——若用户下调 thumbnail_dpr 或更改网格密度，w240/w480 会重新变得有用（届时自动重新生成）。 因此建议做成「按当前配置清理非最优档位」的显式操作而非自动行为，clean_stale_thumbnails() 增加一个"仅保留 floor 及以上档位"的判断即可。

附带收益 实测

  • 首次浏览更快：缩略图编码速度提升 3.3–11×，一页 48 张 w720 缩略图的编码耗时约 780 ms → 234 ms。
  • 滚动更顺：单张 w720 缩略图磁盘读取量 392 KB → 49 KB，一屏 48 张从约 18.8 MB 降到约 2.4 MB。无损 WebP 的解码（Huffman + LZ77 + 预测）也明显慢于有损（DCT）。
  • 降低磁盘压力：用户 C 卷可用空间仅约 40 GB，回收 120 MB 缓存是纯收益。

四、已优化的方向（不建议重复投入）

以下几处是常见的性能瓶颈，但本项目已经处理到位，继续投入的边际收益很低：

方向现状结论
前端首屏体积Vuetify 按单组件目录导入、入口只注册首屏组件、自托管字体、MDI 图标子集化；首屏 JS 约 99 KB gzip已接近下限
SQLite 深翻页两库各自走索引分页 + 流式归并，避免 ATTACH+UNION ALL 的临时 B-tree（实测 offset 25000 由 1362 ms 降至 2.5 ms）已解决
JPEG 缩略图解码走 jpeg-decoder 的 DCT 域 1/2、1/4、1/8 降采样，避免整图解码（原占全链路 80% 时间）已解决
目录扫描与统计dir_listing 5s TTL 缓存 + file_cache 目录 mtime 校验，一次刷新共用同一次扫描已解决
缩略图并发度线程数 = min(核数−2, 内存预算/48MiB)，clamp 到 2–12，避开 UI 与内存争抢已解决
依赖瘦身image 关闭默认 feature 只留 4 种格式；tokio 按需 feature；tauri 未启用 devtools已处理
